### A helper engine keeps its locals on one stack, and only the main thread posts Havok steps
- Files: `crates/engine-core/src/engine.rs` (`stack_key`, `push_frame`), `crates/engine-core/src/real_threads/havok.rs` (`havok_post_ready`), `crates/engine-core/src/real_threads.rs` (its test)
- Upstream approach: a helper engine's stack for `with_stack` locals is chosen by the shared kernel's current game thread, and the engine stops the run if a second game thread asks for locals on the same placed stack, because a helper ran only inside the main thread's fork.
- Fork approach: an engine with a placed stack (a render helper's) has that one stack whichever game thread is current. The Havok helper is posted from whichever game thread steps the world, so it asks for locals as different game threads in one run, and the stop ended the scene soak at frame 121 (nv-rs#997).
- Second part: with the stack stop gone the soak went on to stop at frame 624 ("a coroutine yields only from its own thread" on `nv-havok`): a step posted from game thread 17 waited for a lock another game thread held, and the helper cannot hand the turn over. `havok_post_ready` now needs the main game thread; other threads run the step inline. The rule covers loader and garbage-collection jobs too, because `loader_post_ready` and `post_loader` forward to it (`crates/engine-core/src/real_threads/loader.rs`): those jobs also run inline when posted from a game thread other than the main one.
- Decision: keep
- Reason: a helper runs one job at a time, so one placed stack is correct for it; the owner check was an assumption the Havok helper broke
- Evidence: `a_helpers_locals_stay_on_its_placed_stack_whichever_game_thread_is_current`, `two_helpers_with_placed_stacks_do_not_overlap`, `a_havok_step_is_posted_only_from_the_main_thread` (also asserts `loader_post_ready`); scene soak runs below (pull request)
