### Shader overrides
- Files: `crates/d3d9-wgpu/src/shader_override.rs` (new), `crates/d3d9-wgpu/src/device.rs` (`shader_of`, `draw`, `override_usable`, `override_snapshot`, `override_variant_ready`, `scene_light`, the depth surfaces' usage), `crates/d3d9-wgpu/src/sm/wgsl.rs` (`convert_replaced`), `crates/engine-platform/src/d3d9real.rs` (`want_frame_view`), `crates/host/src/shader_overrides.rs` (new), `crates/host/src/lib.rs`
- Upstream approach: every pixel shader is the conversion of the game's bytecode; no program can read the scene's depth
- Fork approach: a shader named as the packages name it (`WATER033.pso`) can be drawn with a WGSL program of the fork's own (`fn nv_main()` in the converted module's frame) that also reads the scene's depth as distances (a snapshot at the frame's first overridden draw); asked for by a graphics setting or the engineers' `NV_SHADER_OVERRIDES` folder; with none asked, nothing is read, made or drawn otherwise (docs/fork/SHADER-OVERRIDES.md)
- Decision: keep
- Reason: the maintainer wants the far water drawn with a shader of the fork's own that reads the scene's depth (nv-rs#897); the facility is general so other shaders can follow without engine changes
- Evidence: `a_name_takes_every_package_s_bytecode_by_the_device_s_key`, `the_key_stops_at_the_end_token`, `a_missing_name_gives_no_override`, `an_override_replaces_the_body_and_keeps_the_frame`, `the_depth_step_reads_the_surface_it_is_made_for_and_validates`, `a_depth_value_turns_into_its_distance`, `a_folder_s_programs_are_named_by_their_files`, and the device tests in `crates/d3d9-wgpu/tests/shader_override.rs`; Lake Mead pictures with and without an override (pull request)
