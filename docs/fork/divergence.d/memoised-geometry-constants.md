### Memoised geometry constants
- Files: `crates/engine-core/src/engine.rs`, `crates/engine-typed/src/shader/geometry.rs`, `crates/engine-typed/src/shader/accumulator.rs`
- Upstream approach: every geometry's constant set-up computes the inverse of its transform and its world-view product again, and reads the camera, fog and eye words on each draw (nv-rs#937).
- Fork approach: the camera, fog and eye words and the inverse of a transform and the world-view product are kept in direct-mapped thread-local caches. Each key holds the engine's number and every word the answer was made from, so a changed frame, transform or camera misses without a frame counter; a draw with unchanged inputs reuses the words. `Engine` carries a number so an answer from another engine's run cannot be used. The set-ups, the device calls and the constant-map uploads still run in the exe's order; only repeated reads and arithmetic are skipped.
- Decision: keep, offer back when upstream takes per-draw constant work off the main thread.
- Reason: the draw path is about 40% of the game main thread and `setup_geometry_constants` is about 12% of it (docs/fork/PERF.md); these are repeated computations that do not change what is drawn.
- Evidence: the unit tests `the_camera_fog_and_eye_inputs_are_kept_for_the_next_draw`, `the_inverse_is_kept_for_the_next_draw_with_the_same_transform` and `the_world_view_product_is_kept_for_the_next_draw`, and the typed differential cases `setup_geometry_constants`, `world_view_constants`, `inverse_4x4`, `pixel_entry_19` and `eye_pos`. The record-stream, pixel and `NV_PERF` ABBA gates stay with the maintainer: record with `nv-rs-dev scene soak ... --env NV_D3D9_RECORD=...`, compare pictures with `nv-rs-scene compare`, and time with `NV_PERF=1 nv-rs-scene bench ...` plus `nv-rs-scene bench-compare`.
